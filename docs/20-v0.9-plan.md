# Plan: 0.9 - "Instances", an MO2 style manager for any game (draft 2)

Nothing here is built. Draft 1 was too optimistic; this draft lists what is hard, what I do not know, and what has to be checked first.

## 1. What you asked for
A button under the game list that lets you choose the file system yourself: where the game is installed, where it keeps saves, where it reads mods. Then "make it like Mod Organizer 2 where I can fully do everything". Constraints you gave: do not waste disk space; files cannot be signed, so offer a version that runs through Python (`py.exe`) instead of our own exe.

## 2. What makes MO2 work, and what we cannot copy
MO2's whole design rests on **USVFS**: a native DLL injected into the game process that intercepts file calls, so the game sees `Data\` as the merge of all mods while the real game folder is never touched. Everything else (profiles, overwrite, tools) is built on that.

We are stdlib-only Python and our exe cannot be signed. So the honest choices for "the game sees the merged files" are:

| Option | Disk space | Touches game folder | Risks | Verdict |
|---|---|---|---|---|
| A. Hard-link deploy | none | yes, while deployed | **A game or tool that rewrites a linked file in place also changes the mod's original** (same file). Crash leaves links behind. Needs same drive. | Usable only with rules (below) |
| B. Symlink / junction deploy | none | yes | Symlinks need Developer Mode or admin; some games and anti-cheat reject reparse points | Junctions for folders only |
| C. Copy deploy | **doubles** | yes | Slow, wastes space (you said no) | Explicit opt-in only |
| D. Windows Projected File System (ProjFS) | little (files are fetched on first read) | no: a separate virtual root folder | Built-in Windows optional feature, must be enabled once (admin), API is C callbacks reached through `ctypes`; **I have not tried it and cannot test it here** | Research spike, not promised |
| E. WinFsp/Dokan virtual drive | none | no | Needs a kernel driver installed; third-party | Rejected (extra install, trust) |
| F. USVFS-style injection | none | no | Native code, unsigned DLL injection, blocked by Smart App Control and antivirus | Rejected |
| G. Don't deploy: generate the game's own mod list | none | no | Only works for games that load mods from a list or folder (Paradox games, Bannerlord) | **Already what 0.8 does**; keep |

**Proposal:** two engines behind one interface, chosen per instance:
- **List engine** (G) for games that take a mod list or folder: no deploy, no risk. This covers every game the app has today.
- **Deploy engine** (A with rules, junctions for folders) for games that need files in their own folder. ProjFS (D) is a spike to try later because it would remove the "touches the game folder" problem.

### Rules that make hard-link deploy safe
1. **Mutable files are copied, not linked.** Anything matching the instance's "mutable" patterns (`*.ini`, `*.cfg`, `*.json`, `*.xml`, `*.log`, save and config folders) is copied, so the game can edit it freely. Everything else (textures, models, archives, DLLs) is hard-linked, which is where the disk space is anyway.
2. After the game exits, a **write-back scan**: any deployed file whose content changed is moved to the `Overwrite` mod; the link is replaced by a fresh copy first, so a mod original is never altered.
3. **Manifest first**: every created link/copy is written to `deploy.json` *before* it is created, so a crash can always be cleaned up ("Restore game files" on next start).
4. The game's original files are never deleted: a file a mod replaces is **renamed** (`file.rmm-orig`) and renamed back on restore.
5. Steam "verify files" or an update while deployed is detected by the manifest (files missing or changed) and the app offers to restore first.

### The "when does the game end" problem (new, important)
Undeploy needs to know when the game has exited. Steam launches games through a stub, so the process we start often exits at once. Options: watch for the game's executable name (polling `tasklist`), or keep deployed until you press **Restore**, or restore on next start. Draft: poll by exe name when configured, always show a visible "Deployed" banner with a Restore button, restore automatically at the next app start.

## 3. "Any game": what that really means
A generic manager knows nothing about a game. MO2 solves it with a **game plugin per game**. We cannot guess where files go. So:
- **Game templates as data**: JSON files in the app (and ones you can drop in a folder) with name, Steam app id, how to find the install, where saves are, where mods map to (`Data`, game root, `Documents\...\Mods`), which files are mutable, how to start it.
- A **Custom** template with nothing filled in: you pick every folder yourself (your button).
- Templates I would write first are the ones you tell me. **Needed from you: which games.**

### Installing a mod into the right place
Archives rarely match the layout the game wants (an extra top folder, or a `Data` folder inside). MO2 shows a **tree where you pick the folder that is the mod root**. The installer needs the same: auto-detect by the template's marker folders, and a manual "this folder is the root" choice when detection is unsure. This was missing from draft 1.

## 4. Design
- **Instance** = `{id, name, template, game_dir, save_dir, base_dir, engine, mutable[], map[], exe, args, tools[]}`; `base_dir` is the folder you choose and holds `mods/`, `profiles/`, `overwrite/`, `downloads/`, `deploy.json`. It should be on the game's drive for hard links.
- **Mod** = a folder in `mods/` with `meta.json` (name, version, source, nexus id, notes, archive it came from).
- **Profile** = ordered list with enabled flags (our playset) plus its own save folder. Switching a profile with separate saves swaps the save folder by renaming/junction, atomically and only when the game is not running and nothing is deployed.
- **Priority** = list order, last wins, like today. **Conflicts** = file level (already works; the Paradox definition-level scan is not used for custom instances).
- **Tools** = saved executables; running one deploys first, runs, then write-back captures its output in `Overwrite`.
- **Nexus** (later): your API key in Settings, off until entered, stored only on this PC. `nxm://` link handler needs a registry entry for the current user (no admin). Free accounts get the slow download through the site; the app says so.

## 5. The Python edition (no exe)
Windows Smart App Control blocks unsigned exes but runs the signed `py.exe`/`python.exe`. A second download:
- `Ronin-Mod-Manager.pyz` built with `python -m zipapp` (a few hundred KB; no bundled Python, so the smallest option for disk space). Run with `py Ronin-Mod-Manager.pyz`; a small `.cmd` file is included for double-click. If Smart App Control also blocks the `.cmd`, the `py` command line still works; **this must be tested on your PC**.
- Needs Python 3.8+ installed (python.org or the Store); the app is stdlib-only.
- No native window (pywebview is third party): it opens an Edge/Chrome `--app` window, else the browser.
- Self-update downloads the new `.pyz`, checks `SHA256SUMS.txt`, swaps it, restarts through `py`.
- This is independent of instances and could ship first as **0.8.6** so you can use the app now. Recommended.

## 6. Testing without a Windows PC
CI has `windows-latest` runners, so hard links, junctions, renames, `tasklist` polling and the `.pyz` can be tested for real on Windows there, with fake games (a tiny script that writes files and exits). What CI cannot show: Smart App Control, anti-cheat, Steam, and real games. Those stay on a checklist in `docs/13` for your PC.

## 8. Risks
- **Data loss is the main risk** of any deploy engine. Every step is manifest-first and reversible, and the first test builds default to the safe engine (list or "preview only").
- Anti-cheat or online games may reject changed game folders. The app will say it does not support those.
- I cannot test on your games. Expect the first template releases to need your feedback.
- Scope: MO2 is years of work; 0.9 is a base, not parity.
